# 可复制的 agent 提示词

三段提示词都已实战验证（178 本书 / 834 个知识点）。替换 `<尖括号>` 占位符即可用。

**通用约定**：子 agent 看不到你的对话，提示词必须自包含；`note_files` 里的相对路径要显式补上工作目录前缀；必须写明「以磁盘为准」。

---

## 1. 精读（阶段 2，每个 batch 一个 agent）

```
你是知识库架构师。工作目录是 <workspace>。

任务：精读文件 `<work>/batches/<batch>.txt`（UTF-8，用 read 工具；文件较大，若一次读不完就用 offset/limit 分次读完，不要跳读）。
文件里包含若干本书，每本以 `===== BOOK n =====` 分隔，格式为：书名、作者、微信读书分类、进度、`## 划线笔记`（每行一条划线）、`## 我的想法`（用户自己的批注）。

对每一本书输出：
1. `title`：书名（照抄）。
2. `theme`：一句话说清这本书在这位用户的知识体系里承担什么角色（不要复述书名）。
3. `parents`：1-3 个「一级父分类」候选，用简短中文名。可以是已有候选，也可以自创，但同一批次里要统一命名。
4. `topics`：3-8 个「知识点」。知识点必须是可复用、可检索的知识单元，而不是章节标题。
   例如「存货与应收账款持续累积是经营恶化的早期信号」「安全边际的本质是价格与内在价值的缓冲带」。
   每本笔记量很少的书（<5 条划线）给 1-3 个即可，不要硬凑。
   每个知识点要有 `name`（≤20 字）和 `desc`（一句话说明这个知识点讲的是什么）。

另外给出 `category_suggestions`：站在全局角度，你建议设哪些一级父分类，
每个分类要有 `name`、`desc`（这个分类收录什么）和 `reason`（为什么值得独立成类）。控制在 3-6 个。

输出方式（两步都要做）：
A. 先用 write 工具把完整结果写成 JSON 文件：`<work>/survey/<batch>.json`
   （严格 JSON，UTF-8，不要 markdown 代码块包裹，根对象包含 batch/books/category_suggestions）。
B. 然后返回一段紧凑的纯文本汇报，格式：
   第一行 `<batch> | 书籍数=N | 知识点总数=M`
   接下来每行一个分类建议：`分类名 — desc`
   最后一行列出你这一批最核心的 10 个知识点名称（用 / 分隔）。
   注意：返回的文本要短，不要把整个 JSON 复述出来。
```

用 `workflow` 扇出：`agent(prompt, { label, phase, schema })` + `parallel()`。建议给 `schema` 做结构校验。

## 2. 合并（阶段 4，每个分类一个 agent）

```
你是知识库架构师。工作目录是 <workspace>。

背景：一位投资者的微信读书划线笔记正在被整理成 `<out>/` 下的渐进式披露知识库
（`llms.txt` 目录 + 知识点 txt 文件）。11 个一级父分类已确定，本次只处理一个分类：
`<slug>`（<中文名>）。

**重要**：为了不让正文撰写阶段出现「源笔记根本支撑不了这个知识点」的空壳，你在合并时必须遵守：
**每个知识点只能来自候选里真实存在的 `topics`，不要根据书名或主题自行发明候选里没有的知识点**。

步骤：
1. 用 read 工具读完 `<work>/candidates/<slug>.json`。它包含该分类下的所有书，每本书有
   `book`、`author`、`marks`（该书画线数）、`noteFile`、`theme`、`topics`（候选知识点数组，每项有 `name` 和 `desc`）。
2. 用 read 工具（配合 offset/limit）读父分类提案里本分类那一节，了解已规划的二级主题簇；
   再读知识点粒度标准。
3. 产出最终知识点清单，规则：
   - **合并同义**：不同书讲同一件事的候选必须合成一个知识点，绝不能出现两个意思相同的文件。
   - **拆分过宽**：一个候选若其实包含 2-3 件独立的事，按「一个文件只说清一件事」拆开
     （拆分后的每个知识点仍需能追溯到该候选）。
   - **粒度标准**：一个知识点 = 一个可检索的原子判断，能写成「X 是 Y」或「如果……则……」。
     中文名 ≤ 20 字，优先沿用用户笔记里的原话术语。
   - **宁精勿滥**：该分类若有大量只有 1-2 条划线的边缘书，其候选可以合并到同一簇的相关知识点里，
     不要为每本书硬造一个文件。最终数量以「能写出有实质内容的文件」为准。
   - **不要遗漏有实质内容的候选**：候选里有信息量的内容都要被吸收；纯情绪化、无信息量的可丢弃，
     但要在汇报里说明丢了什么、共几条。
   - **归簇**：每个知识点归到 6-9 个二级主题簇之一。
   - **不要越界**：只收录真正属于本分类的内容。若某候选明显属于别的父分类，
     **仍然保留在本分类里**（宁可留也不要丢），但要在汇报里单独列出「疑似越界」及建议归属。
   - **定位来源**：每个知识点记录它来自哪些书，以及后续撰写正文时需要读的原始笔记文件路径
     （来自候选的 `noteFile`）。
4. 用 write 工具把结果写成 JSON：`<work>/kp/<slug>.json`，结构：
{
  "category": "<slug>",
  "category_zh": "<中文名>",
  "clusters": [{"name": "簇名", "desc": "这个簇收录什么（一句话）"}],
  "knowledge_points": [
    {"zh": "中文知识点名", "slug": "english-kebab-slug", "cluster": "簇名",
     "desc": "一句话说明（30-60字，会写进 llms.txt 目录）",
     "sources": ["书名"], "note_files": [".scratch/notes/xxx.md"]}
  ]
}
严格 JSON，UTF-8，不要 markdown 代码块包裹。slug 必须全分类内唯一、纯英文 kebab-case。
5. 返回紧凑汇报（不要复述整个 JSON）：`<slug> | 候选N → 最终M 个知识点 | K 个簇`，
   然后列出簇名和各自知识点数，再列出前 10 个知识点的「中文名 / slug / 簇」，
   最后说明丢弃了几条候选、以及疑似越界的候选项（如有）。
```

## 3. 撰写（阶段 5，每组 6 个知识点一个 agent）

```
你在为一位投资者构建私人知识库。原始素材是他从微信读书导出的**划线笔记原文**
（不是书的全文，也不是你的先验知识）。
工作目录：<workspace>

第一步，用 read 工具读这些文件：
1. 你负责的知识点：`<work>/kgroups/<group>.json`。里面有 `category`（决定输出目录）、
   `category_zh`、`clusters`、`knowledge_points`（每个有 zh/slug/cluster/desc/sources/note_files）。
   **组里有几个知识点就写几个文件**，写完请核对数量。
2. 该分类的全量知识点总表：`<work>/kp/<category>.json`（**只用来查 slug、找「相关」**，
   不要写别人的文件）。
3. 你这组知识点涉及的全部原始划线笔记。注意：JSON 里 `note_files` 写的是
   `.scratch/notes/xxx.md` 这种相对路径，**实际路径要加前缀** `<work>/`，
   即 `<work>/notes/xxx.md`。文件里 `## 划线笔记` 是用户划的原文，`## 我的想法` 是用户自己的批注。

第二步，为每个知识点用 write 工具写一个文件，路径 `<out>/<category>/<slug>.txt`
（UTF-8，纯文本，严格按下面模板）：
```
<把 knowledge-point-spec.md 里的文件模板整段贴进来>
```

写作要求（硬性）：
- **一切内容必须来自你读到的划线笔记**。禁止编造书里没有的数字、案例、结论，
  也禁止用你自己的领域知识补充素材。
- 首行 H1 必须是 `# 中文名 slug`（中文名取自 zh 字段，slug 取自 slug 字段，中间一个空格）。
- `## 判断`：一句话说清核心判断（30-60 字）。
- `## 要点`：2-5 条，每条都是笔记能支撑的实质信息，写成可直接使用的判断句，
  不要写「书中提到……」这类空话。
- `## 边界与反例`：1-3 条。笔记里确实有条件、失效场景或反例时才写；
  没有就写 `- 笔记中未涉及明确边界条件。`（这一小节必须存在，不能省略）
- `## 原文锚点`：1-3 条**原句引用**，格式 `- 《书名》：「原句」`。必须是笔记文件里
  **逐字连续**出现的句子（可截断，一个字都不能改写；**不许用「……」把不相连的两句拼起来**）。
  写完后请逐条在笔记文件里回查是否逐字一致。
- 头部字段：`分类:` 用 category；`主题簇:` 用该知识点的 cluster；
  `相关:` 写 1-3 个**本分类内**其他知识点的 slug（从总表里挑真正相关的，英文逗号分隔，没有写「无」）；
  `来源:` 列出涉及的书名与划线数，格式 `《书名》(N条划线)`、多本用 `、` 分隔
  （划线数从笔记文件头部「划线: N」读）；`证据:` 按来源书数量写 `N 本书互证`，
  只有 1 本时写 `单书孤证`。
- 正文（判断+要点+边界+锚点）总字数控制在 150-400 字。宁可短而实，不要长而空。
- **不要写空壳**：如果某个知识点在它的 note_files 里确实找不到支撑材料，
  **跳过它不写文件**，并在汇报里单独列出。我会另外补源。

第三步，返回紧凑汇报：每个知识点一行 `<slug> | OK | 引用条数`，
被跳过的写 `<slug> | SKIP | 原因`，最后一行写「本组共 N 个知识点，实际写了 M 个文件」。
不要复述文件内容。
```

用一个 `workflow` 调用扇出全部组：

```js
const groups = args.groups;   // 例如 ['financial-statements-g01.json', ...]
const results = await parallel(groups.map(g => () =>
  agent(promptFor(g), { label: g.replace(/\.json$/, ''), phase: '知识点撰写' })));
return { groups: groups.length, settled: results.filter(Boolean).length, reports: /* … */ };
```

## 4. 补写（阶段 5 之后，处理缺文件）

对 `verify-notes.mjs` 报出的「缺文件」清单，用**一个** agent 集中补，而不是每组重跑：

```
你在补写一个知识库中 N 个尚未产出的知识点文件。工作目录 <workspace>。

背景：`<out>/<分类>/<slug>.txt` 里的内容**必须**来自 `<work>/notes/` 下的划线笔记原文。
这 N 个知识点之前因为「指定的源笔记里找不到支撑」而没有写出文件。
现在请你**在整个笔记语料里重新搜一遍**，能写就写，确实不能写就明确判 DROP。

N 个待补知识点：
1. `slug` | 分类 <cat> | 主题簇「<cluster>」| 中文名「<zh>」| 判断要点：<desc> | 原指定源：`<work>/notes/xxx.md`
…

做法：
1. 先 read 上面 N 个指定的源笔记文件（确认它们到底有没有材料）。
2. 用 grep 工具在整个语料目录 `<work>/notes/` 里搜相关关键词，多试几组。也可以用 glob 列举后逐个 read。
3. 对每个知识点：
   - **如果有其他书的笔记能支撑这个判断**：用它写文件，`来源:` 改写成实际取材的书名与划线数，
     `证据:` 按实际来源书数量写。注意：从别的书取材时，知识点的**实质判断必须与找到的原文一致**；
     如果原 desc 跟原文对不上，就按原文改写「判断」与「要点」，不要硬套原 desc。
   - **如果全库确实没有支撑**：不要写文件，判 DROP，并给出你搜过的关键词与结论。

<文件模板与硬性要求同「撰写」>

汇报：每个知识点一行 `<slug> | OK | 实际来源书名 | 锚点条数` 或 `<slug> | DROP | 全库无支撑的具体理由`，
最后列出实际写出的文件路径。不要复述正文。
```

**关键**：DROP 决策前必须确认搜过全库。同一本书的多份笔记文件（见 `data-format.md`）是「假 DROP」的头号原因。
