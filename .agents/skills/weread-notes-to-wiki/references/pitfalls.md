# 实战踩坑记录

全部来自真实项目（178 本书 / 3,641 条划线 → 834 个知识点）。每条给：症状 → 根因 → 处置。

---

## A. 数据层

### A1 同书多记录 → 假 DROP / 空壳文件

**症状**：撰写 agent 诚实汇报「该知识点的源笔记里没有任何相关划线」，于是知识点被跳过；或者更糟——写出一个「## 要点：笔记中未记录可支撑本知识点的实质内容」的空壳。

**根因**：同一本书在 `books/` 里有两个 JSON（换设备或重新导入导致），其中一个只同步到 1 条划线、甚至只是断句残片。候选的 `note_files` 恰好指向了残本。

实例：《手把手教你读财报2》9 条 vs 1 条；《UsaVsUsa》3 条 vs 1 条。这一个原因直接造成 5 个知识点被误删、3 个文件写成空壳。

**处置**：
- `extract-notes.mjs` 会在 `meta.json.warnings` 里列出所有同名书，**阶段 1 必须读完**。
- 建映射时同名书取划线最多的那份。
- 判 DROP 前必须确认该书**所有**笔记文件都读过了；补写流程要用 grep 搜全库（见 `prompts.md` 第 4 段）。

### A2 零划线书

**症状**：某本书在索引里但没有任何知识点。

**根因**：`noteCount = 0`（只加书架或刚开始读）。

**处置**：正常。登记但不产出知识点。**不要因为「书名看起来很重要」就补造知识点**——那必然变成空壳。

### A3 `raw` 字段是字符串套 JSON

`bookmarklist.raw` 和 `myReviews.pages[].raw` 需要二次 `JSON.parse`，外层成功不代表内层能解析。脚本已处理，不要手写解析。

## B. 子 agent 行为

### B1 返回 `null`，但文件其实写了

**症状**：workflow 汇报「完成 8/13」或 `settled` 数少于 agent 数，看起来大失败。

**根因**：`agent()` 带 `schema` 时，若 agent 最终答复不符合 schema（例如话多、格式偏），返回值是 `null`——但它的 write 早已执行。

实测：13 个精读 agent 有 5 个返回 `null`，13 份 JSON 一个不少。

**处置**：**一律以磁盘为准**。汇报只用来定位问题，不作为完成凭据。校验脚本读文件，不读汇报。

### B2 汇报与实际不符

**症状**：agent 说「本组 5 个知识点全部写出」，但组文件里其实有 6 个；或者汇报里出现「SKIP」随后又自我更正说「那是笔误」。

**根因**：agent 在长汇报里对不上自己的清单。

**处置**：`verify-notes.mjs` 的 A 段（清单 vs 磁盘）是唯一权威。缺的就补跑，多的就查来源。

### B3 从书名发明知识点

**症状**：知识点在候选里找不到出处，撰写时源笔记里没有对应内容，最后变成空壳或被 DROP。

实例：`central-local-relation-core`（从《历代经济变革得失》书名推断「中央地方关系」——但那本书只有 1 条划线，是熊彼特的名言）、`state-monopoly-and-power`、`mfn-as-bargaining-chip`。

**处置**：合并阶段的提示词里必须显式写「**每个知识点只能来自候选里真实存在的 topics，不要根据书名或主题自行发明**」。这 4 个字面要求，省掉后面 4 次返工。

### B4 试图用先验知识补写

**症状**：文件的「要点」里出现笔记中没有的数字、机制、案例；或者「原文锚点」被改写成通顺版本。

**处置**：提示词里把「禁止用你自己的领域知识补充素材」写成硬性要求；`verify-quotes.mjs` 做机器兜底。**两者都要有，只靠提示词不够。**

### B5 跳过无支撑项是正确行为

如果提示词写了「找不到支撑就跳过、不要写空壳」，agent 会真的跳过——这是好事。不要因为「缺文件」就训斥它，先按 A1 判断是真缺还是假缺。

## C. 版式与结构

### C1 H1 漏写 slug

**症状**：文件首行是 `# 存货` 而不是 `# 存货 inventory`。

**根因**：模板里 H1 是 `# 中文名 slug`，但 agent 经常只写中文名。**这是最高频的问题**：11 个分类里有 5 个分类共 218 个文件命中。

**处置**：`lint-kp.mjs` 从文件名反推 slug 自动补上。改完检查 idempotent（第二次跑应为 0 修正）。

### C2 漏整个小节

**症状**：文件里没有 `## 边界与反例`。

**根因**：agent 觉得「没有边界内容」就把整节删了。

**处置**：提示词明确写「**这一小节必须存在，不能省略**，没有内容就写占位句」；`lint-kp.mjs` 检查四个小节是否齐全。实测有一批 5 个文件漏了这一节，用补写 agent 单独补齐（比重跑整组便宜）。

### C3 行内粘连标题

**症状**：`- 存货绝对水平上升可能有问题。## 边界与反例` 挤在同一行。

**根因**：agent 在上一节末尾没换行。

**处置**：`lint-kp.mjs` 检测行内出现的 `## ` 并切开，前后补空行。

### C4 `相关` 字段写成中文名或全角顿号

**症状**：`相关: 存货、在建工程长期不转固`、`相关: insulin-over-glucose、ketogenic-gout-risk`。

**根因**：agent 用了中文分隔符或直接写中文知识点名。

**处置**：`verify-notes.mjs` 的 C 段会逐 token 检查，并提示「这是中文名，应写成 slug: xxx」。实测抓到 22 条。`build-index` 不校验这个，所以必须跑 C 段。

### C5 跨分类 slug 冲突

**症状**：同一个 slug（如 `outcome-bias`）在两个分类里各有一个文件。

**根因**：概念确实相邻，两个分类的合并 agent 独立起了同一个名字。

**处置**：不致命（物理文件在不同目录），但会污染交叉引用。给其中一个加语义前缀：`outcome-bias` → `outcome-bias-not-process`，`asymmetric-odds` → `asymmetric-bet-structure`。改完要**同步改同分类内其他文件 `相关` 字段里的旧 slug**。

### C6 知识点挂在未声明的簇上

**症状**：`verify-notes.mjs` B 段报「游离知识点(簇名不存在)」。

**根因**：改簇名时只改了 `clusters[].name`，忘了同步 `knowledge_points[].cluster`。

**处置**：批量改簇名时两个地方一起改，改完必跑 B 段。

### C7 单点簇

**症状**：某个主题簇只有 1 个知识点。

**处置**：并入语义最近的邻簇（连簇名一起改），或确认它确实自成一类。1 个知识点的簇在 `llms.txt` 里看着很怪。

## D. 引文忠实性（最危险的一类）

子 agent 会**在完全无意的情况下**改动原文。实测抓到 4 类，全靠 `verify-quotes.mjs` 兜住：

| 类型 | 原文 | 被写成 | 危害 |
|---|---|---|---|
| 偷删标点 | `…至少不那么容易，因此，我们通过减法…` | `…因此我们通过减法…` | 引文不再逐字，无法回原文定位 |
| 偷删字 | `实值期权和虚值期权距离**期权**到期日越长` | `距离到期日越长` | 同上 |
| 换掉句末标点 | `…以及专家网络，而个人投资者几乎永远无法负担得起这些资源。` | `…以及专家网络。` | 截断处改变了语义边界 |
| 用 `……` 拼接 | `公开讨论我持有的股票是一个坏主意。这倒不是担心…真正的问题在于，它会扰乱我的头脑。` | `…是一个坏主意。……真正的问题在于…` | 引号内出现了原文没有的连续关系 |

**处置**：
- 提示词必须明写「**不许用「……」把不相连的两句拼起来**」。不写这条，子 agent 会觉得省略号是规范做法。
- 修的时候**回原始笔记复制那一段**，不要凭印象重写（很容易引入新偏差）。
- 每次改完重跑 `verify-quotes.mjs`，直到 0 失配。

## E. 校验脚本自身的坑

### E1 先检查后修复 → 假阳性

`lint-kp.mjs` 早期版本在**修正之前**做校验，于是「H1 缺 slug」「缺小节」会全量报错，看起来一塌糊涂。修正后必须**基于修正后的文本**再校验。

### E2 把 `llms.txt` 当成知识点

目录文件也叫 `.txt`。所有「数文件」的地方都要排除 `llms.txt`，否则会出现「应有 72 / 实有 73 / 多 1 个叫 llms」这种噪音。

### E3 索引与文件数对不上

生成索引后再跑一次链接校验。索引条数 ≠ 目录内 txt 数，说明有知识点没写出（或被删了但索引没更新）。

## F. 流程与成本

- **阶段 3 必须停。** 父分类错了，后面几百个文件全废。这是唯一的强制人工门禁。
- **别重跑整组。** 一组 6 个文件里少了 1 个，用补写 agent 单独补，比重跑整组便宜得多。
- **一次 workflow 别塞太多组。** 实测 30 组/次稳定；按分类拆 2–3 次调用便于失败隔离。
- **单个批次别太大。** 单批 >30,000 字时子 agent 会跳读。但单本超大书（《证券分析》21,000 字）不要拆开——拆了会割裂上下文。
- **汇总阶段别在主上下文里塞全量 JSON。** 让子 agent 把结果写到磁盘、只返回紧凑汇报，主 agent 用脚本对账。
