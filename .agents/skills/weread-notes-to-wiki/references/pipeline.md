# 六阶段操作手册

约定：

- `<rawDir>` 微信读书导出目录　`<work>` 工作目录（中间产物）　`<out>` 知识库输出目录
- 参考规模：178 本书 / 3,641 条划线 / 22.7 万字 → 834 个知识点 / 11 个分类，全流程约 130 个子 agent

---

## 阶段 1 · 解析

```bash
node scripts/extract-notes.mjs <rawDir> <work>
```

产出 `<work>/notes/*.md`、`<work>/notes/_index.json`、`<work>/meta.json`。

**验证**

1. `meta.json` 的 `totalMarks` 必须与 `raw/index.json` 的 `summary.highlightTotal` 一致。
2. **逐条读完 `meta.json` 的 `warnings`**：
   - 「同一书名有 N 份笔记文件」→ 记下来，阶段 4/5 引用该书时取划线最多的那份（见 `data-format.md`）。
   - 「0 条划线」→ 这些书登记但**不产出知识点**。
3. 抽查 1 本大书的 md：划线是否按章节顺序、有没有 `## 我的想法` 段。

写入新文件的 header 必须包含 `- 进度: …  划线: N  想法: M`，后面阶段要读这个 N 填 `来源` 字段。

---

## 阶段 2 · 并行精读

```bash
node scripts/make-batches.mjs <work>/notes <work>/batches 12000 2
```

按字数贪心装箱，产出 `batch-NN.txt` + `_manifest.json`。经验值：

- 每批目标 12,000 字，**最大批次不要超过 30,000 字**（单批太大时子 agent 会跳读）。
- 单本书就可能超过目标（例如《证券分析》21,000 字），这是正常的，不要为了均衡把一本书拆开。
- 通常 10–20 批。

用 `workflow` 工具扇出，每个 batch 一个 agent。提示词见 `prompts.md` 的「精读」。要求每本书产出：

- `theme`：这本书在用户知识体系里承担什么角色（一句话）
- `parents`：1–3 个父分类候选
- `topics`：3–8 个知识点候选（`name` + `desc`）；划线 <5 条的书给 1–3 个即可，不要硬凑

**验证**：把各批 agent 的产出汇总，书数与 `_index.json` 对账，覆盖率必须是 100%。

> 子 agent 可能返回 `null` 但文件其实已经写成。**以磁盘为准，不要以汇报为准**——汇报只用来定位问题，不作为完成凭据。这是全流程反复出现的模式。

---

## 阶段 3 · 父分类（硬门禁）

把各批的 `category_suggestions` 和每本书的 `parents` 收敛成 6–12 个一级分类，每个给出：中文名、英文 slug（kebab-case）、一句话描述、覆盖书数/划线数。

收敛规则：

1. 只有**问题域不同、检索意图不同**才拆成两个一级分类。
2. 同一问题域的不同视角合成一个，用主题簇区分。
3. 候选分类若划线权重 < 3% 且不足 5 本书，默认不单独成类。
4. **没有操作结论但有稳定阅读线**的领域可以独立成类（软件工程、哲学人文），但必须在提案里说明为什么值得独立，以及不设「杂项兜底类」的理由。

**然后停下来，把分类表和理由交给用户确认。确认前不许进入阶段 4。**

这一步是整条流水线的成本杠杆：分类错了，后面几百个文件全废。真实案例中用户在此处把 11 类原样通过，但同类流程里也出现过「把估值从价值投资里拆出来」这类调整。

## 阶段 4 · 书→分类映射 + 知识点合并

**4a 映射**：产出 `book-category.json`（`{ "书名": "分类slug" }`），178 本书全部落位，允许一本只归一个分类。

**4b 候选分组**：按映射把阶段 2 的 `topics` 归到各分类下，产出 `<work>/candidates/<slug>.json`，每本书带上 `marks`、`noteFile`、`theme`、`topics`。

**4c 合并**：每个分类一个 agent（并行），产出 `<work>/kp/<slug>.json`：

```jsonc
{
  "category": "financial-statements",
  "category_zh": "财报分析与舞弊识别",
  "clusters": [{ "name": "资产质量与爆雷识别", "desc": "这个簇收录什么" }],
  "knowledge_points": [
    {
      "zh": "存货", "slug": "inventory", "cluster": "资产质量与爆雷识别",
      "desc": "一句话说明（30-60 字，会写进 llms.txt）",
      "sources": ["从现金看财报", "火眼金睛读财报"],
      "note_files": [".scratch/notes/xxx.md"]
    }
  ]
}
```

合并规则：

- **合并同义**：不同书讲同一件事必须合成一条。绝不出现两个意思相同的文件。
- **拆分过宽**：一条候选里含 2–3 件独立的事就拆开。
- **禁止发明**：每个知识点都要能追溯到候选里的某个 `topics` 条目。**不许因为「这本书应该讲 X」而新增候选里没有的知识点**——这类条目 100% 会在阶段 5 变成空壳。
- **不要越界**：明显属于别的分类的候选仍保留在本分类，但在汇报里单独列出「疑似越界 + 建议归属」，供阶段 6 之后统一处理。
- 纯情绪化、无信息量的候选可以丢，但要在汇报里说明丢了几条。

**验证**：`node scripts/verify-notes.mjs` 的 B 段（结构一致性）此时应能跑过——虽然文件还没写，但清单本身要合法（slug kebab 唯一、簇引用有效、中文名 ≤20 字）。

**切组**：按每 6 个知识点切成 `<work>/kgroups/<slug>-gNN.json`。6 是实测的平衡点：再大子 agent 容易漏写，再小调度开销上升。

## 阶段 5 · 并行撰写

用 `workflow` 工具扇出，每组一个 agent。提示词见 `prompts.md` 的「撰写」。

要点：

- 每个 agent 读 **组文件**（要写哪 6 个）+ **分类全量清单**（只用于查 `相关` 的 slug）+ **这些知识点的源笔记文件**。
- `note_files` 里写的是相对路径 `.scratch/notes/xxx.md`，**实际路径要加前缀**。这个前缀必须在提示词里显式给出，否则 agent 会找不到文件。
- 明确要求：**找不到支撑就跳过不写文件**，并在汇报里列出。「宁可少一个知识点，也不要空壳」必须写进提示词。
- 一次 workflow 调用别塞太多组。实测 30 组/次可以稳定跑完；36 组也可以。分批调用（例如按分类拆 2–3 次）便于失败隔离。

**验证**：

```bash
node scripts/lint-kp.mjs <out>/<category>      # 先修版式
node scripts/verify-notes.mjs categories.json <work>/kp <out>
```

`verify-notes` 的 A 段会列出「缺文件」和「多余文件」。缺的那些分两类处理：

- agent 报告了 SKIP → 你要判断这个 SKIP 是**真无支撑**还是**读到了残本**（见 `data-format.md`）。真无支撑就从 `kp/<slug>.json` 里删掉该条目，别留在索引里当悬空链接。
- agent 没报告却缺了 → agent 漏写，补跑那一组。

## 阶段 6 · 校验与生成索引

```bash
# 1. 版式（每个分类都跑；会自动修 H1 与粘连标题）
node scripts/lint-kp.mjs <out>/<category>

# 2. 结构 + 完整性 + 相关引用 + 跨分类冲突
node scripts/verify-notes.mjs categories.json <work>/kp <out>

# 3. 引文忠实性（核心闸门）
node scripts/verify-quotes.mjs <work>/notes <out>

# 4. 生成目录
node scripts/build-index.mjs categories.json <work>/kp <out> <work>

# 5. 链接自洽
node scripts/verify-links.mjs <out>
```

**第 3 步是这套流程存在的意义。** 子 agent 会不知不觉地改写原文——偷删一个逗号、把「因此我们」写成原文的「因此，我们」、用 `……` 把不相连的两句拼成一句。`verify-quotes.mjs` 把每一条 `原文锚点` 拿回原始语料里做子串匹配，一处不中就报出来。真实项目中它抓到了 4 处改写，全部修回逐字原文。

修法：打开报错的知识点文件，**回原始笔记里复制那一段**，不要凭记忆重写。

**第 2 步的 C 段**（`相关` 引用）经常报错，因为子 agent 喜欢在 `相关` 里写中文名或用全角顿号。修法：从本分类的 `kp/<slug>.json` 里查对应的 slug 替换掉。

**第 4 步之后**再跑一次第 5 步，确认生成的 `llms.txt` 里每条链接都能落到真实文件。

---

## 收尾检查

全部绿了之后，人工抽查 3–5 个文件（优先挑：素材最薄的书、术语最专业的分类、你自己熟悉的领域），确认：

- 「判断」句是不是真的由下面的锚点支撑，而不是「听起来对」的通识
- 有没有把模型自己的领域知识混进「要点」
- 素材薄的文件是不是诚实写短了，而不是注水

这一步机器替代不了。
